## 🏛️ 架构总览

### 🎯 核心定位

**Apache ShardingSphere** 定位为 **Database Plus** —— 构建在异构数据库之上的标准化和生态系统。

**核心理念**: 不创造新数据库，而是专注于最大化现有数据库的计算能力。

## 🎨 设计原则与架构优势

### 🏗️ 核心设计原则

#### 1. SOLID原则

- **单一职责**: 每个模块职责单一明确
- **开闭原则**: 对扩展开放，对修改关闭
- **里氏替换**: SPI实现可以相互替换
- **接口隔离**: 接口精简，避免冗余方法
- **依赖倒置**: 依赖抽象而非具体实现

#### 2. DRY原则 (Don't Repeat Yourself)

- 提取公共逻辑到基础设施层
- 复用SQL解析、路由、重写基础能力

#### 3. YAGNI原则 (You Aren't Gonna Need It)

- 不预先实现不需要的功能
- 保持架构简洁，避免过度设计

### 🎯 架构优势

| 维度 | 优势 | 说明 |
|------|------|------|
| **vs 分布式数据库** | 轻量级、保护投资、避免厂商锁定 | ShardingSphere在数据库上层，不替换数据库 |
| **vs 传统中间件** | 功能丰富、生态完善、架构灵活 | 微内核+可插拔架构 |
| **vs 云厂商方案** | 支持多云部署、避免技术绑定、自主可控 | 开源、跨云 |

## 📊 部署模式对比

```
┌───────────────────────────┐    ┌───────────────────────────┐
│  ShardingSphere-JDBC      │    │  ShardingSphere-Proxy     │
└───────────────────────────┘    └───────────────────────────┘

┌─────────┐                   ┌─────────┐
│  App 1  │                   │  App 1  │
│  App 2  │                   │  App 2  │
│  App 3  │                   │  App 3  │
│  ...    │                   │  ...    │
└────┬────┘                   └────┬────┘
     │                              │
     │ 直接连接                      │ MySQL/PG Protocol
     │ (JDBC)                       │
     ▼                              ▼
┌──────────────────┐         ┌──────────────────┐
│  ShardingSphere  │         │  ShardingSphere  │
│     - JDBC       │         │     - Proxy      │
│   (Driver JAR)   │         │  (独立部署)       │
└──────────────────┘         └──────────────────┘

特性对比:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
部署位置:     应用进程内          独立服务器进程
性能:        更好（零网络跳转）    较好（多一次网络跳转）
语言支持:    仅Java              任意支持MySQL/PG的语言
运维成本:     分散（每个应用）     集中（单点管理）
资源占用:     应用进程共享         独立进程
配置管理:     分散（每个应用）     集中（配置中心）
适用场景:     高性能Java应用      多语言、集中管理场景
```

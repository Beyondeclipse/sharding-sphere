# 文档迁移设计文档

## Context

**背景**：
ShardingSphere项目现有文档结构（`openspec/changes/shardingsphere-architecture-proposal/`）采用大文档模式，包含6个大型文档。这种结构适合人类线性阅读，但对AI系统定位效率低下。

**当前问题**：
1. AI定位效率低：需要在长文档中搜索关键词，耗时长且精确度不足
2. 文档结构与代码结构不对齐：难以建立文档与代码的对应关系
3. 更新影响范围大：修改一个大文档可能影响多个模块的描述
4. 缺乏AI专用索引：AI系统没有专门的定位工具

**约束条件**：
- 必须同时满足AI系统和人类读者的需求
- 文档内容不能丢失，只能重组和扩展
- 新文档结构必须易于维护和扩展
- 需要兼容现有的 `openspec` 变更管理系统

**利益相关者**：
- AI系统：需要快速精确的文档定位
- 架构师：需要全面理解架构设计
- 开发者：需要快速查阅特定模块文档
- 维护者：需要易于维护和更新的文档结构

## Goals / Non-Goals

**Goals**：
1. 创建AI友好的文档结构，实现毫秒级定位
2. 保持人类友好的阅读体验，支持线性阅读和按需查阅
3. 建立文档路径与代码路径的镜像对应关系
4. 创建AI专用索引系统（`.ai-index.yaml`）
5. 提供清晰的学习路径和导航机制
6. 实现模块化文档结构，独立更新、互不影响

**Non-Goals**：
1. 不改变任何代码实现或功能
2. 不修改文档内容本身，只进行重组和结构优化
3. 不创建新的功能规格（specs），只优化文档组织方式
4. 不影响现有的 `openspec` 变更管理流程
5. 不强制AI系统使用新结构（兼容性保持）

## Decisions

### 决策1：采用镜像代码结构的文档组织

**选择**：文档路径镜像代码路径
```
代码结构:        文档结构:
infra/route/  →  modules/infra/route.md
features/sharding/ → modules/features/sharding.md
```

**理由**：
- AI可以通过代码路径直接定位文档
- 人类理解文档与代码的对应关系
- 独立更新，影响范围小

**替代方案**：
- 功能分类结构（如 `docs/sharding/`, `docs/routing/`）：难以建立与代码的明确对应关系
- 扁平化结构（所有文档在同一层）：难以管理大量文档

---

### 决策2：创建AI专用索引文件

**选择**：使用YAML格式的 `.ai-index.yaml` 索引文件

**理由**：
- YAML格式易于AI解析和理解
- 支持多维索引：代码路径、类名、标签、功能、问题
- 可扩展性强，易于添加新的索引维度
- 与Markdown文档分离，不干扰人类阅读

**索引维度**：
1. **code_path_mappings**: 代码路径 → 文档路径
2. **class_index**: 类名 → 文档路径 + 用法示例
3. **tag_index**: 标签 → 相关文档列表
4. **feature_index**: 功能关键词 → 文档路径 + 核心概念
5. **problem_index**: 问题症状 → 诊断文档
6. **learning_paths**: 学习路径推荐

**替代方案**：
- 在每个文档中嵌入JSON元数据：增加文档复杂度，影响可读性
- 创建单独的数据库索引：增加技术复杂度，难以维护
- 使用全文搜索引擎：需要额外依赖，不适合静态文档

---

### 决策3：模块化小文档 vs 大文档

**选择**：每个模块一个小文档（25+个文档）

**理由**：
- AI精确定位：直接打开目标文档，无需搜索
- 独立更新：修改一个模块不影响其他文档
- 按需加载：人类可以只阅读相关模块
- 易于维护：小文档更容易保持更新

**权衡**：
- 优点：精确定位、独立更新、按需加载
- 缺点：文档数量多、需要维护交叉引用

**替代方案**：
- 保持6个大文档：AI定位效率低
- 按层次分文档（3-4个中等文档）：仍然不够精确

---

### 决策4：文档迁移策略

**选择**：渐进式迁移 + 并行共存

**迁移步骤**：
1. 创建新的文档结构和索引
2. 迁移现有文档内容
3. 创建新的模块文档
4. 验证所有链接和引用
5. 更新索引和导航
6. 保留旧文档一段时间作为参考

**理由**：
- 低风险：旧文档作为备份和参考
- 可验证：新文档逐步验证
- 可回滚：随时可以切换回旧文档

**替代方案**：
- 快速重构（一次性替换）：风险高，难以回滚
- 完全重写（忽略现有文档）：丢失已有内容

---

### 决策5：文档模板标准化

**选择**：创建统一的模块文档模板

**模板结构**：
```markdown
# [模块名称]

> **代码路径**: `[实际代码路径]`
> **核心标签**: `#tag1` `#tag2`
> **相关模块**: [链接]

## 📋 模块概述
## 🎯 核心接口
## 🔄 工作流程
## 🎨 使用示例
## 📚 相关文档
## 🏷️ 标签索引
```

**理由**：
- 保持一致性：所有文档结构统一
- 易于理解：人类和AI都能快速熟悉文档结构
- 易于维护：模板明确各部分内容

## Risks / Trade-offs

### 风险1：维护成本增加

**风险描述**：
- 文档数量从6个增加到25+个
- 需要维护 `.ai-index.yaml` 索引
- 需要验证大量交叉引用链接

**缓解措施**：
1. 创建文档模板，简化创建流程
2. 使用脚本自动生成基础框架
3. 定期验证链接有效性
4. 建立"谁修改谁更新"的原则

---

### 风险2：学习曲线

**风险描述**：
- AI系统需要学习使用新索引
- 人类读者需要适应新的导航方式

**缓解措施**：
1. 提供详细的README.md和导航指南
2. 创建AI使用说明和学习路径
3. 保留旧文档一段时间作为过渡
4. 提供示例演示定位流程

---

### 风险3：文档一致性问题

**风险描述**：
- 多个小文档可能导致内容重复或不一致
- 交叉引用可能断裂

**缓解措施**：
1. 使用统一的术语表（terminology.md）
2. 定期审查文档间一致性
3. 建立文档审核流程
4. 使用标签系统建立关联

---

### 风险4：索引同步问题

**风险描述**：
- 文档更新后，`.ai-index.yaml` 可能未同步更新
- 索引条目可能过时或错误

**缓解措施**：
1. 建立"文档更新必更新索引"的规则
2. 使用自动化工具检查索引一致性
3. 定期审查索引文件
4. 提供索引更新检查清单

## Open Questions

1. **是否需要创建自动化工具？**
   - 问题：是否有工具可以自动生成模块文档框架？
   - 选项：
     - A. 手动创建（当前方案）
     - B. 创建脚本自动生成框架
     - C. 集成到CI/CD流程
   - 建议：先手动创建，验证效果后考虑自动化

2. **索引更新频率？**
   - 问题：`.ai-index.yaml` 应该多久更新一次？
   - 选项：
     - A. 每次文档变更后立即更新
     - B. 每周定期更新
     - C. 重大变更后更新
   - 建议：每次文档变更后立即更新（低频变更场景）

3. **是否需要版本控制？**
   - 问题：文档是否需要跟随代码版本？
   - 选项：
     - A. 文档独立版本（当前方案）
     - B. 与代码版本绑定
     - C. 使用Git标签管理文档版本
   - 建议：文档独立版本，但在重大代码变更时同步更新

4. **多语言支持？**
   - 问题：是否需要创建英文版本文档？
   - 选项：
     - A. 仅中文（当前方案）
     - B. 中英双语
     - C. 使用翻译工具自动生成
   - 建议：先完成中文版，验证效果后考虑英文版
